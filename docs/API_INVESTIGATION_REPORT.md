### Endpoint 9 — the documented OCDS point is broken

`public.eprocurement.systems` answers `HTTP 200` but the body is a JavaScript
error object, not OCDS:

```json
{"message":"read ECONNRESET","name":"Error",
 "config":{"url":"https://mtender.gov.md/search/complaints?NrProcedurii=…&page=1"}}
```

The response is 200-with-an-error, so any client checking only the status code
would silently store garbage. The pipeline therefore never uses this host.

### Endpoint 10 — internal search API is unreachable

`https://mtender.gov.md/js/static/app.js` (the portal's own bundle) contains a
second, undocumented search backend:

```js
r = "https://public.api.mepps.openprocurement.net/api/2.3"
s = (e, t) => ({ method: "get", url: `${r}/search/${e}${t}` })
```

The host does not respond within 60 s. It is also the wrong layer for this
thesis (an undocumented internal service, not a published data interface), so
it is documented and rejected rather than relied upon.

### Endpoint 3 — how the working parameters were found

Rather than guessing, an invalid parameter was sent deliberately. The service
answered with its own validation message, which named the two accepted
parameters. This is the only documented way the parameter set was established.

## C. The pagination is a date cursor, not a row offset

`offset=0` returns HTTP 500. The working form is `offset=<ISO-8601 timestamp>`,
and the response carries the cursor for the next page:

```json
{
  "data": [
    {"ocid": "ocds-b3wdp1-MD-1539851461397", "date": "2018-10-18T08:31:01Z"},
    {"ocid": "ocds-b3wdp1-MD-1539856317368", "date": "2018-10-18T09:51:57Z"},
    {"ocid": "ocds-b3wdp1-MD-1539856433473", "date": "2018-10-18T09:53:53Z"}
  ],
  "offset": "2018-10-18T09:53:53.000Z"
}
```

Consequences, all handled in `src/mtender/api_client.py`:

* records come back in **ascending `date`** order, so the whole history is
  reachable by following the cursor;
* a page is capped at **300** records (`limit=1000/2000/5000` all return 300);
* the endpoint **intermittently answers HTTP 200 with an empty body** — 7 such
  responses occurred during a single scan — so every call is retried with
  exponential backoff;
* one inventory record carries the placeholder date `1970-01-19T23:36:18Z`
  (Unix epoch 0), which normalisation rejects.

## D. Response structure actually observed

`GET /tenders/{base_ocid}` returns an OCDS 1.1 **package**, not a single
release:

```json
{
  "uri": "http://public.mtender.gov.md/tenders/ocds-b3wdp1-MD-1730452703725",
  "version": "1.1",
  "publisher": {"name": "M-Tender", "uri": "https://www.mtender.gov.md"},
  "packages": [".../tenders/ocds-b3wdp1-MD-1730452703725-PN-…", "..."],
  "records": [
    {"ocid": "…-PN-…", "compiledRelease": {"tag": ["planningUpdate"], …}},
    {"ocid": "…",      "compiledRelease": {"tag": ["compiled"], …}},
    {"ocid": "…-EV-…", "compiledRelease": {"tag": ["awardUpdate"], …}}
  ]
}
```

### Five structural facts that break naive parsing

1. **There is no top-level `buyer` object.** Measured over 40 live packages, the
   key `buyer` is never populated. The procurer is only available as
   `parties[]` entries whose `roles` intersect
   `{buyer, procuringEntity, payer}`, plus `tender.procuringEntity`.
   Taking `release["buyer"]` yields 0 % coverage.
2. **`records` are not ordered by usefulness.** The array mixes a `compiled`
   release with `planning` / `tender` / `awardUpdate` releases, and the *last*
   element is frequently an empty `planning` notice. Using the last release
   instead of merging gives 0 % buyer coverage; `merge_compiled_releases()` in
   `src/mtender/ocds.py` fixes this and lifted buyer coverage from 0/1500 to
   1500/1500 on the test slice.
3. **CPV is published in two different places.** `tender.classification` carries
   the code in 40/40 releases sampled from 2024, while
   `tender.items[].classification` carries it in 38/40 — and many releases have
   `tender.classification` with an empty `items` array. Reading only one of the
   two silently loses codes: after reading both, CPV coverage on a 2019 sample
   rose from **58 % to 100 %** and award coverage from **19.5 % to 67 %**.
4. **`locality` moved.** 2018 packages carry `address.locality`; 2024 packages
   carry `address.addressDetails.locality` (60/60) and
   `address.addressDetails.region` (60/60). A parser that reads only the old
   path loses the buyer location for every recent record.
5. **A tender is often awarded lot by lot.** Up to **219 awards with values** were
   observed in a single package. `estimated_value` is stated for the whole
   tender, so the comparable figure is the **sum** of all award amounts. Measured
   on 266 tenders from 2024: comparing `estimated_value` against the *first*
   award never exceeds 2×, while comparing it against the *sum* does in
   **2.3 %** of cases — using the first award would have hidden every real
   overrun.

## E. Fields that were measured to exist

Party roles observed: `supplier`, `buyer`, `payer`, `procuringEntity`,
`tenderer`, `funder`.
Identifier scheme: `MD-IDNO` (Moldovan fiscal code) — the join key for
blacklist matching.
Classification scheme: `CPV`, at `tender.classification` **and**
`tender.items[].classification`. Currency: `MDL`.
Observed `tender.procurementMethod`: `open`, `limited`.
Observed `tender.status`: `active`, `complete`, `cancelled`, `unsuccessful`,
`planning`. Observed `award.status`: `pending`, `active`, `unsuccessful`,
`cancelled`.

`awards[].suppliers[].id` is authoritative for the winner: across 200 packages
from 2024 all **296/296** award supplier references resolve to a party carrying
the `supplier` role, so no extra role filtering is applied.

The full field-level mapping is in `docs/DATA_DICTIONARY.md`.

### E.1 Coverage depends strongly on the year

Sampled live, not estimated:

| Period | `award_value` | bid data | CPV | buyer identifier |
|---|---|---|---|---|
| 2019-06 (400 records) | 67 % | present | 100 % | 100 % |
| 2024 (250 records) | 56 % | 6 % | 100 % | 100 % |
| 2026-H1 (250 records) | 81 % | 10 % | 100 % | 100 % |

Any feature that depends on bids or on dates therefore has to be read per
period, not across the whole array at once. `no_bid_data` is stored as an
explicit flag for this reason.

## G. Documented limitations

* **No bulk export.** No CSV/Parquet/JSON dump is published, and Moldova is not
  present in the OCP Data Registry, so the full history must be walked page by
  page (300 records per request).
* **No authentication required**, and no rate limiting was observed: 30 parallel
  record requests all returned HTTP 200. The pipeline nevertheless uses a
  conservative concurrency of 6.
* **Award and bid coverage is partial, and it varies by year.** On the first
  1 500 records (late 2018, the platform's pilot period) only 19.5 % carry any
  award or bid data, because most are `planning` notices. Later periods are much
  richer (56–81 % award coverage in 2024 / 2026-H1, see §E.1). Coverage must be
  reported per period, not globally.
* **Intermittent empty list responses.** `GET /tenders/` returns HTTP 200 with a
  zero-byte body for roughly 1 request in 5. The client retries with backoff; a
  silent success check (`status == 200`) is not sufficient, the body must also be
  non-empty.
* **Bid-level values are rarely published** (`bids.details` is present for a
  small minority of procurements), so bid-spread and winning-margin indicators
  cannot be built. See `UNAVAILABLE` in `src/mtender/features.py`.
* **The two documented public entry points are both broken**: the OCDS
  publication point returns an error payload with HTTP 200, and the portal's own
  list endpoint 500s on a numeric offset. Only `public.mtender.gov.md` with a
  date cursor is usable.
* **Placeholder dates exist** in the inventory (`1970-01-19T23:36:18Z`).
* **Suffixed OCIDs return an empty object, not an error.** `…-PN-…` and `…-EV-…`
  respond HTTP 200 with `{}`, so a client that only checks the status code will
  record them as successfully fetched but empty. Only base OCIDs from the list
  endpoint carry a package.

## H. Recommended ingestion method (what was actually built)

```text
GET /tenders/?limit=300[&offset=<cursor>]     -> OCID inventory   (raw_releases)
GET /tenders/{base_ocid}                      -> OCDS package     (raw_tenders, raw_parties)
        merge releases -> normalise           -> norm_tenders, norm_parties
        group stats via $group                 -> features_tenders
        export snapshot + sha256               -> data/features/features.csv
        $group / $bucket descriptive stats     -> results/tables/*.csv
        IsolationForest / LOF / OneClassSVM    -> results/tables/tender_anomaly_scores.csv
        SHAP + permutation importance          -> results/tables/shap_*.csv
```

`raw_tenders` and `raw_parties` are written with `$setOnInsert`, so re-running
ingestion cannot mutate stored raw data, and every run is recorded in
`ingest_runs`.
