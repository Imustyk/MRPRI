## Что установлено при проверке живого API (сентябрь 2026)

- OCID надо брать из списка: суффиксные OCID (`-PN-`, `-EV-`) отдают HTTP 200 с `{}`.
- В одном пакете несколько записей `records[]`, у каждой свой `compiledRelease`: planning notice, сама закупка, уведомление об оценке. Поля надо **сливать**, иначе теряются заявки, награды и стороны.
- Верхнеуровневый `buyer` не заполняется никогда; сторона покупателя ищется через `parties[].roles`.
- CPV публикуется в двух местах: `tender.classification` (40/40 релизов за 2024) и `tender.items[].classification` (38/40). Чтение только одного места теряет коды: покрытие CPV выросло с 58% до 100% после исправления.
- `locality` тоже переехал: в 2018 это `address.locality`, в 2024 — `address.addressDetails.locality`.
- Одна закупка может иметь много наград (наблюдалось 219 в одном пакете). `estimated_value` относится ко всей закупке, поэтому сопоставимая сумма — `award_total`, а не первая награда. При сравнении по первой награде перерасход в 2+ раза не обнаруживается **ни разу**, по сумме — в 2.3% случаев.
- Медиана по CPV считается в MongoDB и в pandas независимо; расхождение после выравнивания определения (среднее двух средних при чётном n, `stdDevSamp`) — 0.

## Ограничения, зафиксированные честно

- Данные о заявках (`bids.details`) публикуются лишь для меньшинства закупок — отдельный флаг `no_bid_data`.
- Прямого признака «закупка у одного поставщика» в ответе нет; `single_bidder` опирается на число заявок.
- Разбивки награды по поставщикам, даты основания сторон, признака «прямоеaward» в ответе нет — см. `UNAVAILABLE` в `src/mtender/features.py`.
- Интерпретационные карты (Grad-CAM) к табличным моделям неприменимы; SHAP используется вместо них.

## Дефекты агрегатных таблиц (05), найденные и исправленные 26.09.2026

Все десять таблиц `results/tables/` формировались без ошибок, но молча теряли
идентифицирующий столбец — файл выглядел корректно, а цифры было нельзя цитировать.

| Симптом | Причина | Исправление |
|---|---|---|
| `year`, `n`, `status`, `method_details`, `n_bidders`, `id`, `name` пустые | группировка по `_id` без переименования в колонку CSV | явный `$project` с переименованием в каждой таблице |
| по одной строке на каждый день, а не на год | `_id` группировался по всему timestamp | группировка по `{"$year": ...}` |
| `n = 1` и `sum_value = 0` в каждом диапазоне | `$bucket` возвращает только `_id`; `{"n": 1}` в `$project` означает «включить поле», а не «посчитать» | `$group` + `$switch` (константа `QUANTILE_BANDS`) |
| суммы занижены | суммировалась первая награда вместо суммы по лотам | `award_total` с откатом на `award_value` |
| `QUANTILE_BANDS` не определена | константа была объявлена в коде, но отсутствовала | границы заданы явно и проверяются тестом на непрерывность |

`award_value` намеренно остаётся только в `cpv_median_by_code`: это знаменатель
признака `value_vs_cpv_median`, и он обязан совпадать с определением признака.

Добавлено 7 регрессионных тестов (33 всего, все проходят), в том числе проверка
на непрерывность границ диапазонов и проверка, что ни одна таблица не вернулась
к `$bucket` или к суммированию первой награды.

## Сессия 26 сентября 2026: кластер, реальный контракт API и UX

### MongoDB переведён в replica set

`mongod` был standalone, поэтому не было транзакций. В `/opt/homebrew/etc/mongod.conf`
добавлено `replication.replSetName: rs0` (бэкап — `mongod.conf.bak-20260926`), сервис
перезапущен, выполнен `replSetInitiate`. Итог: `rs0`, `127.0.0.1:27017`, состояние
PRIMARY, транзакция из нескольких документов проходит. Это **одноузловой** replica set,
а не распределённый кластер. `docker-compose.yml` воспроизводит ту же схему через
сервис `mongo-init` (не проверен: демон Docker не запущен).

Перезапуск оборвал работавший сканер (`NotPrimaryError` на 48 000 OCID). Ничего не
потеряно: `scripts/01a_scan_ocids.py` переписан в возобновляемый (append-only,
дедупликация, безопасный повтор курсора, `--fresh` для перескана), проверено на отрезке
48 000 → 48 599 без потерь и дублей.

### Приложение больше не показывает вымышленные данные

`/api/meta` объявлял `source: synthetic`, хотя `tenders.json` содержал реальные записи.
Контракт UI использовал имена полей, которых в реальных данных **нет**
(`price_to_cpv_median`, `round_price`, `near_threshold`, `bid_spread`, `negotiated_flag`,
`collusion_phone_cluster`). Следствия: фильтр `min_risk` не фильтровал (оценка всегда 0),
фильтры `level`/`procedure` возвращали пустоту, а все шесть вымышленных признаков
отображались как `0.0` — неотличимо от настоящих измерений.

- `backend/app/adapter.py` — сопоставление реальных полей с контрактом UI; всё, чего
  MTender не публикует, возвращается как `null` с причиной
- `backend/app/store.py` — реальный `tenders.json` + `anomaly_scores` из MongoDB
- `POST /api/pipeline/run?source=synthetic` → **409** без `confirm=true`: раньше он
  затирал реальные записи вымышленными

### Найденные при этом дефекты

| Симптом | Причина | Исправление |
|---|---|---|
| `min_risk` не фильтровал | в реальных данных нет `price_to_cpv_median`, и оценка была 0 | контракт переведён на реальные поля |
| «конкуренция» считалась по `n_bids` | `bids.details` — запись на **лот**, а не на участника (10 items → 10 записей; 202 лота → 503) | `n_bidders` — единственная мера конкуренции, `n_bid_records` помечен как счётчики записей |
| `single_bidder_share` = 0.0 | ETL пишет `0/1` целыми, адаптер проверял `is True` | `_flag`, принимающая `1`/`1.0`/`True` |
| `single_bidder_share` занижена в 5 раз | `n_bidders == 0` — это отсутствие данных, а не нулевая конкуренция; знаменатель был равен **всем** строкам | знаменатель — только записи с опубликованным списком участников |
| `/api/stats` → HTTP 500 | NaN/inf из `value_vs_cpv_median` (деление на нулевой медианный CPV) | `_num` отбрасывает нечисловые значения |
| 10 таблиц в `05` с пустыми колонками | `$bucket` возвращает только `_id`; `{"n": 1}` в `$project` — это «включить поле», а не «посчитать» | `$group` + `$switch` (см. предыдущую запись) |

**Следствие для текста главы 3:** доля процедур с одним участником — **43.3 %** среди 293
процедур, опубликовавших список участников (а не 8.5 %, которые показывались раньше при
делении на все 1 500 строк, включая 1 207 без списка). Среднее число участников — 2.44,
а не 0.48. Прежнее число было занижено более чем в пять раз.

## Внешняя валидация и IDNO (этап 9)

**Идентификатор поставщика.** MTender крайне редко публикует объект
`parties[].identifier` — фискальный код лежит в самом идентификаторе стороны в
виде `MD-IDNO-<код>`. Исправлено в `src/mtender/ocds.py` (`_IDNO_IN_ID`,
`_identifier_scheme`) и в `src/mtender/normalize.py` (`_idno_from`).
Раньше идентификатор был `null` у **всех** награждённых записей выборки.

Важный нюанс: `raw_tenders` хранит уже извлечённые документы, поэтому исправление
не применилось к уже сохранённым записям ретроспективно. Код сохранился в поле
`winner_id`, поэтому `_idno_from()` восстанавливает его на этапе нормализации —
это чтение поля, реально присутствующего в документе, а не домысливание.
Результат: **289/289** награждённых записей (100%) теперь имеют
`winner_identifier` и `winner_identifier_scheme = "MD-IDNO"`.
Побочный эффект: IDNO видны и в API/UI (поле `winner_idno`).

**Сверка с чёрным списком AAP (спецификация §13).** Новый этап
`scripts/09_external_validation.py` (подключён к `run_pipeline.sh` как шаг 9).
Ограничение зафиксировано явно: список AAP публикует **только названия** — ни
IDNO, ни фискального кода, ни tender/contract id, поэтому соединение по
идентификатору невозможно (`identifier_matching_possible: false`).

Методика нечёткого сопоставления документирована: регистр, диакритика,
пунктуация, точки в сокращениях (`S.R.L.`, `S. R. L.`) и сокращённые/полные
формы юрлиц. Полное равенство = `exact_normalised`; подстрочные совпадения
вынесены отдельно как `ambiguous` и никогда не считаются совпадениями.

Результат по текущему срезу из 1 500 процедур: **2 совпадения из 22** (0 неоднозначных,
20 без совпадений), 4 награды. Оба поставщика имеют реальный IDNO и оба находятся
в верхнем дециле перцентиля (91,5 и 89,7), но их полоса риска — `low`, то есть
сработал только один детектор. Двойная интерпретация сохранена, а не сглажена:
ранжирование атипичным подтвердилось, согласия детекторов для повышения полосы не хватило.

**Тесты:** 68 passed (было 64). В тестах обнаружены и исправлены два реальных
бага нормализации имён: `S.R.L.` превращался в `s r l` (пунктуация удалялась до
снятия формы юрлица) и не обрабатывалась полная форма
«Societatea cu Răspundere Limitată».
